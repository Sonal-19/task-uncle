# Task Uncle

Bun workspaces monorepo: `apps/api` (Elysia + Drizzle + Postgres) and `apps/web` (Vite + React 19 + TanStack Router/Query + Tailwind v4).
Architecture mirrors `~/Developer/Projects/finance-tracker`.

- Production `.env` needs `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` (`bunx web-push generate-vapid-keys`, once per environment; new keys = every device re-subscribes on next open).
- Ports: web **3500**, API **4500** in dev (Vite proxies `/api`), **4600** in production. Prod: **https://taskuncle.com** on server `oc` (Tailscale, `root@oc`), behind the Cloudflare proxy (`conf/task-uncle.conf`: real IPs from `cloudflare-real-ip.conf`, sw.js/index.html/manifest `no-cache`, Let's Encrypt via webroot `/var/www/letsencrypt`; the old tu.u4.lol and task-uncle.com.u4.lol 301 here, tu.u4.lol keeps `/api/` and serves `conf/legacy-sw.js` as `/sw.js` (on the server `/var/www/task-uncle/legacy/sw.js`) so old installed apps unregister and move over; server `.env` `ALLOWED_ORIGINS=https://taskuncle.com,https://tu.u4.lol`). Server files: `/root/task-uncle/server` (`server.js`, `.env`, tmux `task-uncle-api`), static in `/var/www/task-uncle/front-end`, DB `task_uncle` (role `task_uncle`). Schema changes: push with `drizzle-kit push` through an SSH tunnel (`ssh -fN -L 55432:localhost:5432 root@oc`) before `bun run deploy`. khata-connect uses 3400. DB: `task_uncle` on local Postgres (`apps/api/.env`, see `.env.example`).
- Commands: `bun run dev` (both apps), `bun run typecheck`, `bun run check` (biome), `bun run db:push`, `bun run db:seed` (`-- --reset` replaces data with the demo), `bun run icons` (re-renders PNG icons from `apps/web/public/logo.svg`), `bun run deploy[:backend|:frontend]`.
- Domain: **Event** (project/area) → **Category** (group; `kind: team` when it has `memberIds`, derived, never stored) → **Task**. A task's `eventId` and `categoryId` are both optional (nullable): a category decides the event, a task can sit in an event without a category, or in neither. `placeTask` (shared types) is the one rule for where a task lands after a change (API `resolvePlace` + web reducer); moving to another event without naming a category drops the old one. Code that looks up a task's event/category must handle null. People are assignees (no accounts). Everything is manual CRUD; the only automation is reminders.
- Shared code: `apps/api/src/lib/shared/types.ts` (domain types, enum value lists, `DataState`, `DEFAULT_SETTINGS`, `statusPatch`, `kindOf`, `newId`) is pure TS imported by both apps (`$/lib/shared/types`; web's `lib/types.ts` re-exports it). The DB enums are built from those lists. The web gets API types through Eden (`@api` → `Server`).
- Ids are UUIDs made by the **client** (`newId()`), so rows created offline keep their id. Creates are idempotent: `POST` with an existing id returns the saved row (`onConflictDoNothing` + select). Deletes are idempotent (200 even if gone).
- API: every response is `ok()` / `fail()`; the web unwraps with `call()` / `callMsg()` (`lib/api.ts`). Logged-in routes use `protectedUser` and are grouped in `controllers/index.ts`. Every query filters by the session `user.id`; ids from a body (eventId, categoryId, memberIds, assigneeId, log taskId) are checked with `lib/services/ownership.ts`. Serializers in `lib/services/serialize.ts` turn rows into the exact shared shapes (ISO strings).
- Auth: opaque token in an httpOnly `token` cookie (`core-auth-service.ts`, same as finance-tracker). Sign-up `POST /auth/register` (name, email, password; emails unique, lower-cased; `/register` page → logged in → dashboard), login, logout, `/auth/me`, password reset by emailed OTP (dev: `123456`). One login page for everyone: `homeFor(user)` sends `role = admin` to `/admin`, others to `/dashboard`. `users.status` `disabled` can't log in and their sessions stop working (`authProcessor` treats them as guests). `db:seed` creates `admin@taskuncle.app` / `uncle@123` as admin and `demo@taskuncle.app` / `demo@123` as a regular user holding the demo data (dev only); promote anyone with `bun run --cwd apps/api db:make-admin <email>`. The web caches the user (`stores/auth-store.ts`, `tu-user`, type `PublicUser`) so it opens offline; `useSession` re-checks `/auth/me`, any 401 logs out. `users.last_login_at` is set by `startSession`, `last_seen_at` by `userCacheService.touch` (≤ every 5 min).
- Admin panel (`admin-controller.ts` behind `protectedAdmin` — 404 for non-admins; web `routes/_app/admin/*`, guarded by `admin/route.tsx`). Admins get only the admin panel: `_app.tsx` renders `AdminShell` (sidebar / phone bottom tabs from `ADMIN_NAV`, no add-task, reminders, sync, search or task pages) and redirects any other `_app` route to `/admin`; no push sync for admins. Pages: Overview (stat cards link into the others), Users (+ `users/$userId`), All tasks (`/admin/tasks`, every user's tasks read-only, filters in the URL: `status` pending|in_progress|done|overdue|all, `userId`, `priority`, `q`, `page`; API `GET /admin/tasks`, 50 per page), Devices (`/admin/devices`, live sessions grouped by user, `?view=multi`; `GET /admin/sessions`), Reminders log (`/admin/reminders?userId=`; `GET /admin/reminders`), and on phones a More tab (`/admin/more`) for the pages not in the bottom bar (`ADMIN_NAV[].tab`). Admin pages data via `hooks/use-admin.ts`, online only, not the outbox): overview (users, logged-in users = live `auths` sessions, users on 2+ devices, push devices, pending/done/overdue tasks, sign-ups and completions per day, recent logins), users list (search, role/status filter, inline notifications switch), create/edit users (role, notifications), set password, disable/enable, log out one device or everywhere, delete (cascades). Only these routes read across users (task titles/status for the admin's All tasks view; never notes or checklists). Guards: no self-demote/disable/delete, always ≥1 active admin. `users.notify_permission` `off` (admin-set) = no reminders at all: the scheduler skips them, `/push/devices` refuses, and the web engine, SW background check, banner and Settings respect `user.notifyPermission`.
- Status: `pending | in_progress | done` + timestamps (`startedAt`, `completedAt`). Status changes always go through `statusPatch(row, status, at)` — the API with the edit's `editedAt` (capped at now), the web's optimistic copy with the op's `at` — so both agree. No boolean columns: on/off settings are `"on" | "off"`.
- Offline & sync (`apps/web/src/lib/offline/`), local-first like finance-tracker: the TanStack Query cache is persisted to IndexedDB (`idb.ts`, `PersistQueryClientProvider`, busted per build via `__APP_VERSION__`). **Every** write goes through `queue()` in `sync.ts`: the op is applied to the cache at once by the pure reducer `applyOp` (`apply.ts`, mirrors the API: cascades, kind, statusPatch), stored in the outbox (`outbox.ts`, zustand → IndexedDB) and sent in order by `flush()` (network/5xx → retry with backoff, 409 → "Kept a newer change… Use mine", other 4xx → parked as failed in the sync panel with retry/discard, 401 → logged out, ops kept). Ops must stay deterministic and idempotent (send whole values, e.g. the full `subtasks` list, never toggles) because pending ops are replayed over every fresh server response. Edits to an unsent create fold into it; deleting an unsent row just drops its ops. Edits carry `baseUpdatedAt` (server `updatedAt`; optimistic rows keep it) + `editedAt` (`lib/utils/sync.ts` `editVerdict`). Logout wipes IndexedDB (`forgetDevice`); a different user's data is dropped (`claimDevice`). Import/reset-demo need a connection and drop pending ops.
- Hooks: components never call the API or the outbox directly — they use `hooks/use-data.ts` (query keys in `lib/query-keys.ts`, all start with `"tu"`; GETs in `lib/fetchers.ts`). Pages must prefer cached `data` over `error`.
- Amounts are integers in paise; display only via `formatAmount` / `formatAmountShort` (`lib/format.ts`), forms use `toAmount` / `fromAmount`.
- Dates are `yyyy-MM-dd` strings, task time is `dueTime` `"HH:mm"`; use `DateInput` (dd/MM/yyyy, custom calendar) and `TimeInput` (hour/minute grid + AM/PM), never `<input type="date|time">`.
- Every dropdown is `SelectField` (`components/common/select-field.tsx`, over `ui/select`): pass `options` `{value,label}[]`, `""` is allowed. Never a native `<select>`. Pickers inside phone drawers must not rely on scrolling (the drawer's scroll lock blocks portalled popovers).
- Daily tasks: `repeat: "daily"` + `repeatTime` ("HH:mm") + `doneDates` (`yyyy-MM-dd` list, `checkDay` keeps it a sorted set). The task stays `pending`; its check (row, swipe, detail sheet, notification "Mark done") ticks off one day (`setTaskDay`, sent as the whole list like `subtasks`; the SW's direct PATCH uses `tickDay`). It reminds once a day at `repeatTime` in the user's zone, ignoring quiet hours and the `reminder` interval, skipped when that day is ticked, until Repeat is set back to Once ("Stop repeating"). Daily tasks have no due date; the detail sheet shows the last 14 days (tickable) and the streak.
- Reminders: the rules are shared, `apps/api/src/lib/shared/reminder-engine.ts` (`dueReminders`, `nextReminderAt`, quiet hours, overdue boost = half interval, repeat = per task `reminder`: `inherit` → `settingsEvery` (`customMinutes` 5 min–7 days when set, else the `interval` preset; Settings → Custom), a preset, `custom` → the task's own `reminderMinutes` (task form → Remind me → Custom…), or `off`; both custom editors use `components/common/duration-picker.tsx`, `planReminders` = sort + ≤3 single + 1 summary, `toPushPayload`), timezone-aware (`settings.timezone`, reported by the browser in `useReminders`; server falls back to `DEFAULT_TIMEZONE`). Three senders, never two at once:
  1. **Server, Web Push (VAPID via `web-push`, no Firebase)**: `reminder-service.ts` checks every 60 s for users with a `push_subscriptions` row, stamps `lastRemindedAt` (no `updatedAt` bump), writes the log, pushes data-only payloads (TTL 1 h, topic per task) via `push-service.ts`, deletes 404/410 subscriptions. Works with the app closed; an offline device gets them on reconnect. Routes `/api/push/config|devices|devices/remove|test`; subscriptions belong to the session (removed on logout). Without `VAPID_*` env it is off.
  2. **In-app engine** (`hooks/use-reminders.ts`, mounted in `AppShell`, one tab via Web Lock `tu-reminders`, which also keeps Chrome from freezing/discarding it): runs from the cached data only when `serverReminds()` is false (offline, or this user has no push device), queues `task.reminded` + `log.add`. No polling: one timer sleeps until the earliest `nextReminderAt` (≤ 2 min), re-planned when tasks/settings/push data change and run at once on visible/online/offline/pageshow/`resume`.
  3. **Service worker background check** (`periodicsync` `tu-reminders`, Chrome installed app, browser-chosen frequency): reads the persisted query cache from IndexedDB and reminds when no window is visible and the server isn't pushing; dedupes with its own `sw-reminded` map.
  Browser side: `lib/push.ts` (myasta's pattern: `enablePush` from a click, `syncPush` on every logged-in load, `resetPush` on logout, `registerBackgroundCheck`); granting permission anywhere (`usePermission`) also subscribes; Settings → "When the app is closed" toggles it and Test goes through the server. `src/sw.ts` draws pushes with **Mark done / Snooze 1h**; a tap goes to an open tab (`task-action`, queued so it works offline), else straight to `PATCH /api/tasks/:id` with the cookie, else opens `/tasks?task=<id>&action=…`. iOS Safari only gets push for the installed (Home Screen) app.
- Launch splash (installed app only): inline `#splash` in `index.html` (no JS needed, shows an offline note), faded by `lib/splash.ts` once the query cache is restored (min 0.9 s, gives up at 5 s); iOS gets matching `apple-touch-startup-image` JPEGs in `public/splash/` rendered by `bun run icons` (not precached); Android draws its own from the manifest `background_color` (#4338ca, the splash colour). The offline cache is kept 30 days (`maxAge`/`gcTime`).
- PWA: hand-written `apps/web/public/manifest.webmanifest` (app shortcuts `?new=task|event`, handled by `useLaunchAction` in `app-shell.tsx`); the custom SW precaches the whole app shell and waits for `SKIP_WAITING` (`registerType: "prompt"`), registered in `lib/pwa.ts` ("A new version is ready" toast, applied by itself when hidden and synced; keeps `beforeinstallprompt` for the one-click Install button / iOS steps in `install-app.tsx`). `InstallCard` sits on top of the dashboard: desktop only when the browser offers the install, phones always until installed (Android often withholds `beforeinstallprompt`; without it the button shows the browser-menu steps, iOS the Share steps). `PermissionBanner` covers Allow / blocked (per-device unblock steps) / iPhone outside the installed app ("How to install") / plain-http pages. Both are dismissed per device in localStorage (`INSTALL_DISMISSED`, `NOTIFY_DISMISSED`, never the synced settings) and come back on the next login (`offerInstallAgain()` in `useLogin`). Notifications, push and install need a secure context: testing on a phone via the dev server's LAN `http://` address shows the "needs https" banner. Fonts are bundled (`@fontsource-variable/plus-jakarta-sans`) so the app looks right offline.
- Keyboard shortcuts: actions and keys in `lib/shortcuts.ts` (`n` add task, `shift+n` event, `shift+p` person, `g d/t/e/c/p/n/s` go to, `/` search, `shift+r` sync, `?` cheat sheet, `mod+enter` save the open form). Listener `useGlobalShortcuts` (`hooks/use-shortcuts.ts`), handlers in `app-shell.tsx`; plain keys are ignored while typing or with a sheet open. ⌘K search stays in `command-search.tsx`. A new action needs an entry in `SHORTCUT_ACTIONS` and a handler.
- Phones (<768px): bottom tab bar + FAB, sheets are vaul drawers (`ResponsiveSheet`), swipe a task row right = done, left = snooze 1h, the header shows only the logo + user name (no page title, no greeting, no account menu; Settings / Log out are under the More tab). Desktop: account menu (avatar) in the header, sidebar (Install + sync status above the account) + dialogs.
- Open sheets from anywhere with `useSheets()` (`stores/sheet-store.ts`); the FAB and the `n` shortcut pre-select the event/category of the current route.
